# 系统翻译引擎

## 什么时候读

改翻译逻辑、加语言、怀疑翻译走了云端、要评估速度内存、或翻译结果异常（报错、空译文）时。

## 引擎是什么

macOS 的 `Translation.framework`，服务进程 `translationd`。模型是系统资产，装在
`/System/Library/AssetsV2/com_apple_MobileAsset_UAF_Translation_Assets`（只读预装）。
用户级的 `~/Library/Translation/AssetsV3` 只是镜像（符号链接），删掉它不影响"已安装"判定。

## 两种调用方式，选哪个

| 方式 | 场景 | 特点 |
|---|---|---|
| `TranslationSession(installedSource:target:)` | 纯命令行 / AppKit 应用 | macOS 26+，不需要 SwiftUI，直接用 |
| SwiftUI `.translationTask(configuration:)` | 需要下载提示或自动选路 | 必须挂在视图上，宿主用 NSHostingView 也行 |

两者在本机都走设备端，都**不会**联网翻译。

## 三种语言状态

`LanguageAvailability().status(from:to:)`：

- `installed`：已下载，可翻译
- `supported`：系统有模型但没下载
- `unsupported`：系统没有该语言模型（例：瑞典语）

## 语言包机制（重要）

- 第三方应用**不能代下载**语言包。实测在 `supported` 语言对上调用
  `prepareTranslation()`，约 4.6 秒后以 `internalError` / `operation was cancelled` 失败，
  包目录无变化、无网络下载。`canRequestDownloads` 返回 true 也不代表能装。
- 唯一可靠路径：跳转 `系统设置 → 通用 → 语言与地区 → 翻译语言` 让用户勾选。
  deep link：`x-apple.systempreferences:com.apple.Localization-Settings.extension`
- 中英包体积：共用编码器 113 MB + 中文侧 87 MB + 英文侧 62 MB ≈ **262 MB**。
  加日语不重下编码器，只追加一对 decoder。

## 服务器路径不存在

关了「设备端模式」也照样本机跑。实测三组证据：

1. 翻译期间 `translationd` 的 TCP 连接为 0，CPU 时间约等于墙钟时间
2. 删除用户级语言包目录后，状态仍为 `installed`，速度不变
3. 换成系统不支持的语种，直接返回 `unsupportedTargetLanguage`，没有任何网络回退

结论：框架只有"本机模型"和"报错"两条路。Apple 的服务器只服务 Safari 网页翻译和 Siri。

## 实测性能（M 系列，单核）

| 场景 | 结果 |
|---|---|
| 中 → 英 2 万字 | 28 s，约 700 字/秒 |
| 英 → 中 2 万词（11.2 万字符） | 43 s，约 2600 字符/秒 |
| 单段 200 字 | 0.2 s |
| 连续 6 轮 12 万字 | 无衰减、无内存增长 |
| `translationd` 常驻内存 | 280 MB（英译中峰值 600 MB） |
| 单次翻译 CPU | 约 1.4 ms/字，占满一个核 |

成本跟**输出长度**走：中译英输出膨胀约 2.3 倍，所以比英译中慢 3 倍多。

## 分块

- 单块 400–2000 字都可用；2000 字一块吞吐略高
- 优先按段落切，超长段落再按句末标点切
- **必须先把硬换行合并**，否则句子被切碎，译文会断在荒谬的位置
- `translate(batch:)` 与逐块调用耗时相同，内部就是串行，不必为并行写复杂代码

## 已知弱点

- 数字与量词：`三万六千五百零一块` 会被译成错误的英文数字，金额、编号、日期要做占位符保护
- 专名：半文言文本里的人名地名直接走音译
- 语域：现代书面语可用，文言、成语、诗词会塌
- 偶发大小写瑕疵（如 `configUration`），长文零星出现，需要后处理兜

## 屏幕 OCR（做全屏覆盖时用）

Vision `VNRecognizeTextRequest`，`zh-Hans + en-US`，accurate 模式：

- 2560×1440 整屏、2700 字：首次 14.8 s（加载模型），之后 **820–830 ms/屏**
- fast 模式 100 ms，但中文直接崩，不可用
- 会认错字（`三十日内` → `三十日末`），错误会传染给译文

OS 级调用 Vision 需要完整权限，受限沙箱下返回 `unknownError`。

## 覆盖层坐标（踩过的坑）

Vision 的 `boundingBox` 是**归一化、原点左下**的坐标。乘上图片宽高之后，得到的已经是
"左下原点"的像素坐标，直接除以缩放就是视图坐标——**不要再做一次 Y 翻转**。
第一版多翻了一次，结果所有译文块整体跑到屏幕下半部，用户看到的就是"完全没盖到原文"。

正确换算：

```
sx = 图片宽 / 屏幕宽（点）    sy = 图片高 / 屏幕高（点）
x  = rect.minX / sx          y = rect.minY / sy      // 不要再 高度 减 maxY
```

比例必须用"图片实际尺寸 ÷ 屏幕点尺寸"算出来，不要写死 `backingScaleFactor`：
SCDisplay 给的是点（1512×982），抓屏配置乘 2 得到 3024×1964 像素，两者都可能变。

### 精度策略

- **逐行成块**，不要合并成段落再画一个大框：合并后的并集往往跨行跨栏，
  视觉上就是"框在空白处、没盖住字"
- 过滤太小的元素（少于 4 字、高度低于 ~7 pt），菜单栏小图标、进度条会被误识别成文本
- 实测：真实截屏 3024×1964，逐行 80 块，批量翻译 **0.95 s**，整条链路约 2 s

### 校准方法

拿一张真实截屏，用 `--overlay-image 截图.png --overlay-debug --no-present` 跑一遍，
只输出坐标不显示覆盖层，然后核对已知地标：菜单栏时间应落在 y≈958/982、x 靠右；
Dock 名称应落在 y≈20–60。数字对得上，位置就是对的。
